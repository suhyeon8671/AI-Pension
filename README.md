# AI-Pension

미래에셋증권 AI Festival — 연금 Agent 과제 (주제1: 대고객 연금 질의 / 주제2: 상품 설명)

## 폴더 구조

```
AI-Pension/
├── data/
│   ├── institution/   # 제도·세제 문서 (원본 PDF/DOCX/XLSX/PPTX)
│   └── products/      # 투자설명서 등 상품 문서 (상품코드별 폴더, 원본 PDF)
├── extracted/
│   ├── institution/    # institution 문서 추출 결과 (표 JSON, 텍스트 JSON, 청크 JSON)
│   └── products/       # products 문서 추출 결과 (상품코드가 doc_id)
├── structured_store.db  # 표 데이터 SQLite(FTS5) — build_structured_store.py 산출물 (git 미포함, 로컬 생성)
├── vector_store/chroma/  # 청크 임베딩 Chroma persistent store — build_vector_store.py 산출물 (git 미포함, 로컬 생성)
├── scripts/
│   ├── extractors.py            # 포맷별 추출기 (PDF/DOCX/XLSX/PPTX) 공용 모듈
│   ├── extract_tables.py        # PDF 표/텍스트 추출 CLI (단일 파일, extractors.py 래퍼)
│   ├── extract_all.py           # data/ 전체 일괄 추출 + 청크 생성 (병렬)
│   ├── chunk_text.py            # 페이지별 텍스트 → RAG용 청크 JSON
│   ├── build_structured_store.py # 표 JSON → SQLite(FTS5) 구조화 저장소
│   ├── embeddings.py            # 임베딩 프로바이더 (tfidf 기본 / sentence_transformers / hyperclova)
│   ├── build_vector_store.py    # 청크 JSON → 임베딩 → Chroma 적재
│   ├── search.py                # 검색 인터페이스 (semantic_search / table_search) + CLI
│   └── router.py                # 질의 분류(제도/세제/상품/복합) + 검색 라우팅 + CLI
├── api/
│   └── server.py                # 평가용 API 서버 (FastAPI, GET /answer)
└── requirements.txt
```

## 처리 방침

연금 데이터는 성격이 다른 두 종류로 나뉜다.

- **정형 데이터 (표)**: 세액공제 한도, 위험등급, 총보수, 수익률처럼 숫자·조건이 명확한 표.
  `extract_tables.py`로 뽑아서 그대로 구조화 DB(또는 JSON 레코드)로 사용.
- **서술형 데이터 (텍스트)**: 제도 설명, 투자전략, 투자위험 안내 등 문장 형태의 정보.
  `chunk_text.py`로 의미 단위 청크로 나눠서 임베딩 → Vector DB에 적재 (RAG).

표는 pdfplumber로 추출 시 격자선이 있는 표는 잘 뽑히지만, 이미지로 삽입된 표나
색상 박스로 디자인된 표(예: 위험등급 바)는 깨질 수 있다. `extract_tables.py`는
빈 값만 있는 표를 자동으로 경고 출력하니, 해당 페이지는 이미지로 렌더링 후
VLM으로 재추출하는 것을 검토한다.

모든 청크와 표 레코드는 `source_doc`(원본 파일명)과 `page`(페이지 번호)를
메타데이터로 포함해서, 최종 답변에 근거 문서를 표시할 수 있게 한다.

### 이미지 기반 페이지 재처리 (VLM)

institution 문서 중 17개(doc1, doc2, doc3, doc4, doc5, doc8, doc9, doc21, doc24,
doc27, doc28, doc30, doc31, doc32, doc37, doc54, doc56), 총 126페이지는 원본
PDF의 폰트 인코딩이 깨져 있어 텍스트 레이어 자체가 없다(글자 하나하나가
이미지로 심어진 형태 — HWP→PDF 변환 시 흔한 케이스). `pdfplumber`뿐 아니라
`pdftotext`로도 텍스트 추출이 안 되는 걸 확인했고, 반대로 poppler(`pdftoppm`)로
페이지를 이미지 렌더링하면 시각적으로는 완전히 정상 표시된다 — 즉 텍스트
추출로는 원천적으로 복구 불가능하고 VLM(이미지를 읽어서 텍스트화)이 필요한
케이스다.

대회 측 Q&A에서 "전처리·구조화 작업에 사용하는 OCR/VLM은 HyperCLOVA X가 아닌
다른 모델을 써도 무방하다"고 명시적으로 확인했다(최종 답변 생성만 HyperCLOVA X
필수). 이번 세션에서는 별도 API 비용 없이 Claude Code 세션 내에서 126페이지를
직접 읽어 텍스트/표를 옮기는 방식으로 처리했다. 페이지를 poppler로 렌더링한
뒤 VLM으로 재추출한 텍스트/표 레코드에는 `extraction_method: "vlm"` 필드를
추가해서, 자동 추출과 구분하고 원본 페이지(`doc_id` + `page`)로 항상 검증할 수
있게 했다.

향후 유사 문서가 추가되면 같은 패턴(pdftoppm 렌더링 → VLM 판독 → text/tables
JSON에 병합 → chunk_text로 청크 재생성)을 반복하면 된다. 아직 별도
스크립트(`render_page_as_image.py`)로 자동화하지는 않았고, 이번엔 수작업으로
처리했다 — 문서량이 많아지면 스크립트화 또는 Claude API 기반 자동화를 검토할 것.

### products 위험등급 표 보정 (`fix_risk_grade_tables.py`)

products 문서에서 "투자위험등급" 6단계 바(1=매우높은위험 ~ 6=매우낮은위험)는
격자선이 아니라 배경색 박스로 셀을 구분하는 그래픽이라, pdfplumber가 셀 인식에
실패하는 경우가 있다. 실패 유형은 두 가지였다: (A) 라벨 셀이 통째로 빈 문자열로
잡히는 경우, (B) 라벨 텍스트가 줄바꿈 때문에 여러 행으로 쪼개져 들어가 단일
셀로는 안 잡히는 경우.

먼저 "1~6 등급 숫자가 순서대로 있는 행은 있는데, 6개 표준 라벨
(매우높은위험/높은위험/다소높은위험/보통위험/낮은위험/매우낮은위험) 중 일부가
표 안에서 안 잡히는 표"를 자동 탐지해서 실제 영향 범위를 확인했다 — products
100개 문서, 총 6,425페이지 중 **59개 표(39개 문서)**. 이 6단계 라벨은 운용사와
무관하게 금융투자협회 표준 투자설명서 서식이라 문구·순서가 항상 동일하다는 걸
서로 다른 3개 운용사(키움/브이아이/KB) 원본 페이지를 poppler로 렌더링해 직접
대조하여 확인했다. 따라서 institution 때처럼 59페이지를 전부 VLM으로 다시
읽는 대신, 등급 숫자 행 뒤에 오는 깨진 라벨 영역을 검증된 표준 라벨로 직접
덮어썼다. 라벨 영역 뒤에 라벨과 무관한 내용(다음 섹션 제목 등)이 섞여 있어
경계가 애매한 경우는 자동 보정 없이 건너뛰도록 보수적으로 짰다 — 59건 중
58건은 자동 보정됐고, 1건은 직접 확인한 결과 애초에 깨진 게 아니라(괄호 형식
`(매우높은위험)`으로 이미 정상 추출된 변형) 손대지 않았다. FTS5로 "위험등급"
검색 시 바로 찾을 수 있도록 표 맨 앞에 `"투자 위험등급: N등급"` 헤더 행도
추가했다(N은 원본 설명 문단에서 정규식으로 추출). 원본을 덮어쓴 이력은 git
커밋으로 남아있어 필요하면 대조할 수 있다.

**주의**: 이건 "products 전체가 검증됐다"는 뜻이 아니다. 이번 탐지는 딱
"1~6 등급 숫자 행 + 표준 라벨 매칭 실패"라는 좁은 패턴만 잡아낸 것이고, 이
패턴에 해당하지 않는 다른 종류의 표 깨짐(예: 수수료표, 수익률표의 열 밀림 등)은
별도로 검증되지 않았다. 전수 검증이 아니라 샘플 기반으로 발견한 문제이므로,
비슷한 방식(표준화된 고정 서식 여부 확인 → 해당하면 자동 탐지·보정, 아니면
VLM 재처리 검토)의 점검을 다른 표 유형에도 확장할 필요가 있다.

**추가로 발견/수정한 것**: 표 데이터만 고쳐놓고 실제 질의 경로(`router.py`)를
안 고치면 무용지물이라는 걸 뒤늦게 확인했다. 두 가지 문제가 더 있었다.
1. `classify()`의 `use_table_search`가 세제 키워드(`TAX_KEYWORDS`)에만
   반응해서, "위험등급"처럼 표에 있는 사실을 묻는 상품 관련 질의는 애초에
   `table_search()`를 호출하지 않았다 → `TABLE_FACT_KEYWORDS`(세제 + 위험등급/
   보수/수수료/수익률/설정액)로 확장해서 해결.
2. FTS5로 "위험등급"을 검색하면, 상관없는 "변경이력" 표(개정 로그에 "투자위험등급
   변경(4등급→3등급)" 같은 문구가 있어 우연히 걸림)가 먼저 잡히는 경우가 있었다.
   표 맨 앞에 넣은 헤더가 `"투자위험등급: N등급"`(붙여쓰기)이라 FTS5 토크나이저가
   "위험등급"과 다른 토큰으로 인식해 애초에 안 걸리기도 했다 → 헤더를
   `"투자 위험등급: N등급"`(띄어쓰기)으로 바꾸고, 상품코드가 특정된 질의는
   `table_search`에 `product_code`를 넘겨 그 상품 표만 우선 검색하도록
   `route_search()`를 수정했다. (완전히 1순위로 뜨지는 않는 케이스가 남아있지만
   `k=5` 내에는 포함되는 것을 확인함.)

### 상품 마스터 & 클래스별 총보수 (`build_product_master.py`, `extract_class_fees.py`)

대회 자료가 상품 데이터를 상품분류/위험등급/판매 클래스/총보수/수익률/AUM
6축으로 평가한다고 명시해서, products 표를 원문 그대로 검색에 맡기는 대신
필드별로 구조화한 "상품 마스터"를 만들기 시작했다. 각 필드는 단순 값이 아니라
`{value, page, evidence, method, confidence}` 구조로 저장해서, 신뢰도 낮은
값은 Agent가 답변에 안 쓰도록 걸러낼 수 있게 했다.

1차로 `product_name`/`asset_type`/`risk_level`을 뽑았다 (100/100 문서 성공,
`product_name`만 표 헤더 혼입·펀드 개명이력 등으로 3건 confidence<0.7 플래그).
`asset_type`은 펀드명 끝의 괄호(`(채권)`, `[주식]` 등)에서, 여러 개의 괄호가
있으면(펀드코드 괄호가 자산유형 괄호 뒤에 하나 더 붙는 경우가 흔함) 알려진
자산유형 어휘와 일치하는 괄호를 우선한다.

클래스(판매 클래스)·총보수는 표 레이아웃 편차 때문에 별도 스크립트로 분리했다.
"클래스+총보수" 표 194개(83개 문서)가 pdfplumber `extract_tables()`에서
셀이 뭉쳐 깨진다는 걸 확인했는데, `vertical_strategy`/`horizontal_strategy`
(`lines` vs `text`)와 `text_x_tolerance`를 조정해봐도 글자 뭉침은 나아져도
열 분리는 안 됐다 — 즉 표 인식 자체가 실패하는 케이스라 설정 튜닝으로는
한계가 있었다. 그래서 `page.extract_words()`로 각 단어의 실제 좌표(x/y)를
직접 읽어서, top(y좌표)이 비슷한 단어를 한 줄로 묶고 그 줄에서 소수 3~4개
(총보수/판매보수/동종유형총보수/총보수·비용, "동종유형총보수"는 `-`로 빠질
수 있어 3개까지 허용) + 정수 4개 이상(1/2/3/5/10년 비용예시)이 있으면
데이터 행으로 판별해, 가장 왼쪽 소수를 총보수로 클래스 코드(괄호 안 텍스트,
예: A2/C1/Ae/C-E)와 함께 추출하는 방식(`extract_class_fees.py`)으로
전환했다. 이미 정상 추출된 표(KR5120420039)로 방법을 먼저 검증(A2/C1/Ae/
C-E 4개 클래스 전부 일치)한 뒤, 실제로 깨진 문서 2곳(KR5111420047 6클래스,
KR5111450067 4클래스)에 적용해 원본 페이지를 렌더링해서 육안으로 전부
일치함을 확인했다.

처음엔 표의 `총보수` 칸 하나만 남기고 판매보수/동종유형총보수/총보수·비용/
연도별(1·2·3·5·10년) 비용예시/판매수수료(문구)는 계산은 해놓고 저장을 안 해서
버리고 있었다 — 표에 있는 값을 다 뽑아야 하는데 일부만 남긴 실수였다.
`class_code`/`sales_commission_desc`/`total_fee`/`distribution_fee`/
`peer_avg_fee`/`total_fee_and_cost`/`cost_projection_per_10m`까지 표의 전체
열을 담도록 고쳤다. `sales_commission_desc`("납입금액의 N%이내" 또는 "없음")는
셀이 줄바꿈으로 2줄에 걸쳐 있어("납입금액의"와 "N%이내"가 서로 다른 줄) 하나의
정규식으로는 못 잡아서, 두 조각을 각각 찾아 조합하는 방식으로 처리했다.

사용자가 직접 다른 문서(KR510902511M)를 대조하다가 이 문구가 **3줄**로도
쪼개진다는 걸 추가로 발견했다("납입금"/데이터 줄에 낀 "액의 N%"/"이내") -
±1줄로는 못 잡아서 ±2줄로 넓혔더니, 이번엔 바로 옆 클래스 행의 판매수수료
문구를 잘못 가져오는 더 나쁜 문제가 생겼다(C 클래스가 A 클래스의
"납입금액의 0.10%이내"를 그대로 잘못 가져옴). "틀린 값은 없는 값보다
나쁘다"는 원칙에 따라 ±2 확장은 폐기하고 안전한 ±1만 유지 - 이 3줄 분할
케이스는 `sales_commission_desc: null`로 남는 걸 감수했다(핵심 값인
`total_fee` 등은 영향 없음). 판매수수료 인식률은 이 조정 후 332건 중
287건(86%).

**대상 페이지 선정 로직에 진짜 버그가 있었다.** 처음엔 "뭉쳐서 깨진(blob)"
페이지만 좌표 기반 재구성 대상으로 삼았는데, 표가 두 페이지에 걸쳐 있고
앞쪽 페이지는 정상 추출·뒤쪽 페이지만 깨진 경우(KR514X450008에서 실제 확인:
4개 클래스 중 A/C는 정상 추출된 5페이지에, Ae/Ce는 깨진 6페이지에 있었음)
정상 페이지 쪽 클래스를 통째로 스킵하는 문제가 있었다. 좌표 기반 재구성이
이미 정상 추출된 표에도 똑같이 정확하게 동작한다는 걸 검증했으므로(위
KR5120420039 사례), "클래스"+"총보수"가 언급된 페이지는 깨졌든 안 깨졌든
전부 대상으로 삼고 바로 다음 페이지도 후보에 포함하도록 바꿨다.

이 과정에서 클래스 코드 인식 로직의 두 번째 버그도 발견했다: 클래스명이
페이지 경계에서 잘려서 "이 줄"에 라벨이 없으면 "이전 줄"까지 찾아보게
했었는데, 그 "이전 줄"이 사실은 **위쪽에 있는 다른 클래스 행의 이름 꼬리**인
경우가 있어서(KR514X450008에서 Ae 클래스의 총보수(1.16)가 엉뚱하게 C
클래스로 잘못 라벨링된 뒤 중복 제거 로직에 의해 조용히 버려짐 - "틀린 값이
없는 값보다 나쁘다"의 실제 사례) 다른 클래스의 값을 잘못 갖다 붙이는 결과가
나왔다. 클래스 코드는 "이 줄"과 "다음 줄"에서만 찾도록 고쳐서, 못 찾으면
틀리게 붙이는 대신 `class_code: null`로 정직하게 남기도록 했다.

문서)보다 훨씬 넓게 잡혔다. class_code 인식 실패(confidence 0.5)는 84개
문서 중 18개. 중복 클래스코드/범위 밖 total_fee 값은 0건(자동 검사).
검증 문서를 4개→6개로 늘려서(KR5120420039/KR5111420047/KR5111450067/
KR514X450008/KR5118201004/KR5110501016) 총 24개 클래스 값을 원본 페이지와
육안 대조, 전부 일치 확인. **이건 "총보수 표"만 대상으로 한 결과이고,

**총보수/수익률 표 전체 커버리지 재점검 (사용자가 "이런 표 모든 파일에
가능한거지"라고 물어서 실제로 세어봄)** — 상품 100개 중 총보수 84개 문서/
수익률 97개 문서에서만 뽑히고 있어서, 못 뽑은 문서 16개(총보수)/3개(수익률)를
직접 열어봤다. 총보수 쪽 16개 중 **14개가 같은 원인**이었다: 신영자산운용
등 일부 서식은 총보수 %값을 "1.18%"처럼 %를 붙여 한 토큰으로 낸다
(`extract_words`가 공백 없는 "1.18%"를 통째로 한 단어로 묶음). 기존
`DECIMAL_RE`(`^\d+\.\d+$`)는 순수 소수만 매칭해서 이 토큰들이 아예
안 걸렸다 → 해당 페이지에 소수 3개 이상이라는 최소조건 자체를 못 채워
전체 행이 통째로 스킵됐다. `DECIMAL_RE`에 `%?`를 허용하고 저장 시 벗겨내는
식으로 고쳤는데, 그러자 새 문제가 하나 더 나왔다: 판매수수료 문구("납입금액의
N%이내") 탐색 정규식이 이제 %가 붙은 총보수 값 자체("0.145%")를 먼저 찾아버려
진짜 판매수수료율("0.1%")을 놔두고 총보수 값을 잘못 판매수수료로 오인했다 →
탐색 텍스트에서 이 행 자신의 총보수류 토큰들을 먼저 제외하도록 수정해서
해결. 재검증한 7개 기존 검증 문서는 전부 회귀 없음 확인 후 전체 재실행,
**385개 레코드(97개 문서)**로 증가.

클래스코드가 괄호 밖(예: `A(수수료선취-오프라인)`처럼 코드가 괄호 *앞*에
붙고 괄호 안엔 설명만 있는 문서 등) 또는 세로로 회전된 옆면 캡션("투자실적
추이 (연평균 수익률)")이 라벨 줄 사이에 끼어드는 문제로, 아래 수익률 표

**evidence 필드가 값의 근거를 다 안 보여주는 문제 발견·수정** — 사용자가

`sales_commission_desc: "납입금액의 1%이내"`인데 `evidence`에는 "액의 1%"만
있어서(납입금이란 단어가 없음) 값이 어디서 왔는지 의심스럽다고 지적했다.
원본을 다시 보니 "납입금액의 1% 이내"라는 문구가 데이터 줄 위/아래로 3줄에
걸쳐 쪼개져 있었다("납입금" / "액의 1%"+데이터 / "이내") - 값 자체는 ±1줄
윈도우로 정확히 재구성됐지만, `evidence`는 데이터 줄 자기 자신만 담고 있어
그 근거를 안 보여준 거였다. `sales_commission_evidence` 필드를 새로 추가해
sales_commission_desc 판정에 실제로 쓴 ±1줄 윈도우 전체를 그대로 남기도록
했다 - 판정 로직 자체(±1 범위)는 그대로 두고 그 결과를 투명하게 보여주기만
하는 변경이라 ±2로 넓혔다가 사고났던 것과는 무관하다. 이제 A-e처럼
null로 남은 값도 `sales_commission_evidence`를 보면 왜 못 찾았는지(3~5줄로
더 넓게 쪼개져 있어 "납입금"이란 단어가 ±1 범위 밖에 있었음) 바로 확인
가능하다. 전체 재실행 결과 값 자체는 변화 없음(385건 그대로) - 순수
투명성 개선.

**"없음"/"-" 표기 통일 + peer_avg_fee의 숨은 "-" 정보 손실 발견·수정** —
사용자가 두 가지를 지적했다.
1. `sales_commission_desc`가 원본에서 "없음"이라는 글자로 나오든 그냥
   "-"만 찍혀 있든 의미는 같은데("판매수수료 없음") 출력에 굳이 "없음"
   이라고 해석해서 쓰고 있었다 - 원본에 실제로 보이는 기호인 "-"로
   통일했다.
2. `peer_avg_fee`(동종유형총보수)가 자꾸 null로 나오는 게 이상하다고
   지적해서 원본을 다시 봤더니, KR5111420047의 C-P 클래스처럼 이 칸에
   원본이 실제로 "-"를 찍어둔(동종유형총보수 정보가 없다는 걸 확인해서
   알려주는) 경우가 많았다. 그런데 우리 코드는 소수 3개(총보수/판매보수/
   총보수·비용)만 세고 "-"는 애초에 숫자가 아니라서 세지도 않다 보니,
   "이 칸이 통째로 없는 문서"와 "이 칸은 있는데 값이 -로 확인됨"을
   구분 못 하고 둘 다 null로 뭉뚱그리고 있었다 - sales_commission_desc
   에서 이미 겪었던 것과 같은 "확인된 부재 vs 모름" 정보 손실 문제였다.
   판매보수와 총보수·비용 사이(동종유형총보수 칸의 x좌표 범위)에 단독
   "-" 토큰이 실제로 있는지 확인해서, 있으면 `peer_avg_fee: "-"`로
   명시하도록 고쳤다.

전체 재실행 결과 `peer_avg_fee`가 null인 행이 83건→**19건**으로 줄었다

**사용자가 전체 class_fees.json을 다시 붙여넣고 "수정된거맞아?"라고
재검증을 요구해서 발견한 3건의 열 밀림 버그** — 단순 재검토가 아니라
`cost_projection_per_10m.1y`가 비정상으로 작은(10 미만) 행, 큰(500 초과)
행, `distribution_fee > total_fee`인 행, `total_fee_and_cost < total_fee`인
행을 각각 전수 스캔해서 찾아냈다. 넷 다 "숫자 개수만 보고 왼쪽부터 순서대로
컬럼에 배정"하는 기존 방식의 근본적인 약점이 원인이었다:
1. **판매보수가 소수점 없이 정수 하나로만 나오는 경우**(KR5153420318/
   KR5153450785, 실측: "1" - 원본 PDF 글자 자체가 그렇게 찍혀 있고 옆
   숫자들과 폰트·크기 동일함을 확인, 추출 오류 아님). 판매보수 칸이
   `decimals`(소수 정규식) 목록에서 통째로 빠지면서 그 다음 소수(동종유형
   총보수)가 판매보수로, 그 "1"은 엉뚱하게 1년 비용예시로 잘못 흘러들어갔다.
   총보수와 그 다음 소수 사이 x좌표에 정수 토큰이 정확히 하나 끼어 있으면
   (비용예시 정수들은 훨씬 오른쪽이라 안 걸림) 판매보수 자리로 되돌리도록
   고쳤다.
2. **판매수수료("납입금액의 N%이내") 문구의 퍼센트 숫자가 데이터 줄 자체에
   얹혀 나오는 서식**(KR5123490013/16/17, KR5157450090, KR5125450070,
   KR5139420015, KR5152420028, KR5123420015/49, KR5114420016 등 다수).
   "납입금액"은 윗줄에, "의 N%"만 데이터 줄에 걸치면서 이 %값도 소수
   정규식에 걸려 `decimals` 맨 앞에 끼어들었고, 그러면 진짜 4개 컬럼(총보수/
   판매보수/동종유형총보수/총보수·비용)이 통째로 한 칸씩 밀려 읽혔다(총보수
   자리에 판매수수료%가 들어가고, 총보수·비용 값은 아예 유실됨 - 원본과
   대조해 실측으로 확인). 실제 컬럼은 최대 4개뿐이라 소수가 5개면 맨 왼쪽은
   무조건 이 판매수수료%라 드롭했고, 소수 4개인 경우(정상 케이스와 개수가
   같아 구분 안 됨)는 맨 왼쪽 소수가 "%"로 끝나면서 바로 앞/뒤에 "의"
   (납입금액"의") 또는 "이내"가 붙어 있을 때만 골라 드롭했다(KR5113420069를
   원본과 대조하다가 "액의" 바로 뒤에 하필 진짜 총보수 값이 오는 경우를
   발견해서, "%"로 끝나야 한다는 조건을 추가로 걸어 오탐을 막았다).
3. **표에 "총보수·비용" 칸 자체가 없는 문서**(KR5194450018). 총보수/
   판매보수/동종유형총보수 3개 컬럼뿐인데, 기존 로직은 "소수 3개=총보수/
   판매보수/총보수·비용(동종유형총보수는 -로 없음)"이라고만 가정해 왔던
   터라 세 번째 소수(실제로는 동종유형총보수)를 총보수·비용으로 잘못 읽어
   `total_fee_and_cost < total_fee`라는 앞뒤가 안 맞는 값이 나왔다. 헤더에
   "총보수·비용" 표기(가운뎃점+비용 - "총비용예시"의 "총비용"과는 다름,
   가운뎃점 글자가 ㆍ/▪/･/· 뿐 아니라 유니코드 사용자영역(PUA) 글자로도
   나오는 걸 KR5111450067에서 확인해 폭넓게 잡음)가 있는지로 이 칸의 존재

1. **표 첫 클래스 행이 판매수수료 없이 바로 표 헤더 아래에 오는 경우

   "없음"/"-"인 클래스는 애초에 "납입금"이라는 말이 근처에 없어서 표

   운용전환일 전일까지" 같은 문구는 헤더가 아니라 그 행 자신의 실제

3. **더 심각한 버그**: 클래스가 여러 개를 한 묶음으로 취급해 변동성/비교지수

   또한 클래스 코드가 확실히 잡힌 행은 "주변 줄에 변동성 언급이 있으면
   변동성 행"이라는 느슨한 규칙을 아예 적용하지 않도록 해서 재발을 막았다.

하나를 공유). 텍스트는 병합 영역 안 한 줄에만 찍히고 나머지 행은 그 줄에
날짜가 없어 보여서, 줄 단위로만 보던 기존 로직은 이걸 놓쳤다. 인접 줄 순서로
막연히 전파하면(예: "바로 다음 행에 날짜 있으면 이 행에도 적용") 실제로는
안 겹치는 행에까지 잘못 번질 위험이 있어(검증 중 확인: A-e와 병합되지 않은
C-e의 날짜가 A-e로 잘못 넘어감), 대신 `page.rects`로 PDF에 실제로 그려진 셀
테두리를 찾아 그 테두리 범위 안에 들어오는 행에만 정확히 전파하도록 했다
(`_apply_merged_cell_dates`). 이 과정에서 수익률이 전부 "-"인 클래스
(예: 방금 언급한 C1처럼 아직 실적이 없는 클래스)도 값은 없지만 class_code/
설정일은 있는 유효한 행이라 더 이상 버리지 않고 잡도록 확장했는데, 그러면서
새로 생긴 오탐 2건도 같이 잡아 고쳤다: (1) 운용전문인력표의 "이름 생년(예:
전준필1996)"이 대시와 붙어 있는 줄이 대시 개수만으로 걸려 수익률 행으로
오인됨(한글 바로 뒤에 붙은 숫자는 유니코드 `\b`가 경계로 인식 못 해 기존
생년 필터가 못 걸렀음 → 토큰 단위 직접 비교로 수정), (2) 총보수 표의
비용예시(천원, 정수) 행이 대시 사이사이에 정수가 끼어 있는 경우("- - 240
244 40 40 200 204 -") 대시만 세어 수익률 행으로 오인됨 → 값 영역 안에
순수 정수 토큰이 섞여 있으면 제외하도록 추가.

**세로 회전 캡션 문제 수정** — 남은 `class_code:null` 원인을 재확인하려고
사용자에게 전체 파일을 보내줬는데, 표 옆 여백에 "투자실적\n추이\n(연평균\n

캡션 목록과 겹쳐서, "이전 줄"을 건너뛰고 더 멀리(바로 위 비교지수 행
전체)까지 가져와버려 그 행의 "비교지수" 텍스트가 섞여 들어가는 바람에
변동성 행이 class_return으로 잘못 분류되는 문제였다. class_code 탐색
(label_search_text)은 캡션을 건너뛴 줄을 계속 쓰되, "수익률\n변동성"
판별에 쓰는 prev/next 줄은 캡션 건너뛰기 없이 "바로 옆 줄"만 보도록
분리해서 해결(이 판별은 애초에 "바로 옆 줄"이라는 엄격한 인접성이
전제된 로직이라 멀리 갈수록 위험함).

기존 검증 문서 8개(위 5개 + KR5111420047/KR5127420039/KR5118201004)

**"class_return에서 -부분이 null로 뜨는게 있던데"라는 지적으로 발견한
class_fees와 같은 종류의 문제** — `values`의 각 기간(1년/2년/3년/5년/
설정일이후) 값이 소수가 아니면(주로 "-") 전부 `null`로 남기고 있었다.
class_fees의 `peer_avg_fee`/`sales_commission_desc`에서 이미 사용자
지적으로 고친 것과 똑같은 문제 - "추출을 못 해서 모른다"와 "원본이
확인해서 없다고 밝혔다"(신설 클래스라 2년/3년/5년처럼 아직 안 지난
기간에 원본이 직접 "-"를 찍어둔 경우)가 구분이 안 됐다. 실측으로 전수
확인해보니 **56건**의 class_return 행에서 이 문제가 있었고, evidence를
보면 예외 없이 전부 원본이 실제로 "-"라고 찍은 자리였다(추출 실패로
추정되는 사례 0건). 원본 토큰이 정확히 "-"면 "-"를 그대로 남기고, 그
외 미확인 케이스만 `null`로 남기도록 고쳤다.

DB 적재(`build_product_facts_db.py`)는 그대로 둬도 안전하다 - `to_float()`
가 "-"를 숫자로 못 바꾸면 이미 `None`으로 떨어지게 돼 있어서(같은 함수를
class_fees의 peer_avg_fee "-" 값에도 이미 쓰고 있었음) SQL의 REAL 컬럼엔
여전히 NULL로 들어간다. JSON에서만 "모른다"와 "원본이 -라고 밝힘"을
구분해서 보여주고, SQL은 원래 목적(숫자 비교/집계)대로 NULL로 통일.

전체 재실행 후 재확인: 519개 행(97개 문서) 그대로, `values`의 null 개수
56건(부분 null 포함 행 기준)→**0건**, 그 자리에 "-" 238개 값으로 정확히
치환됨, DB 재적재 에러 없음.

발견한 세 가지 문제** — 사용자가 캡처를 같이 보내줘서 원본과 바로
대조할 수 있었다. 문제는 세 가지였다.

1. **최근3년/최근5년 칸이 원본에서 통째로 비어 있으면(설정된 지 얼마
   안 된 펀드) 라벨이 밀린다** - "최근1년 최근2년 최근3년 최근5년
   설정일이후" 5칸 헤더인데 실제 값은 "4.23 4.48 4.48" 3개뿐이었다.
   순서대로 `PERIOD_LABELS[0,1,2]`에 채우던 기존 방식은 이걸 "1y,
   2y, 3y"로 잘못 채웠는데, 3번째 값은 사실 최근3년이 아니라
   설정일이후 값이었다(2y와 정확히 같은 값이길래 "설정일이후"라고
   써야 할 자리를 "3y"로 잘못 부른 것 - 이 펀드가 최초설정일과
   "최근2년" 구간 시작일이 거의 같아서 우연히 값이 같았을 뿐). 헤더
   줄에서 "N년"/"설정일이후" 라벨의 x좌표를 찾아두고, 값 토큰을
   순서가 아니라 x좌표가 가장 가까운 헤더 칸에 매칭하도록 고쳤다.
   (처음엔 페이지 전체에서 "N년" 토큰을 찾아서, 같은 페이지의
   "운용전문인력" 표나 각주 문장에 있는 엉뚱한 "1년"까지 잘못 앵커로
   써버리는 회귀가 있었다 - 여러 "N년" 라벨이 한 줄에 다 같이 나오는
   진짜 헤더 줄만 인정하도록 좁혀서 해결.)
2. **클래스는 있는데 비교지수/수익률변동성이 없는 클래스가 있었다** -
   원인은 중복 제거 로직. 비교지수/변동성 행은 class_code가 애초에
   없는데(None), 같은 상품 안의 여러 클래스가 비교지수 값까지
   우연히 똑같이 나오는 경우가 실제로 있었다(이 문서 실측: 초단기
   우량채/Class A/Class Ae/Class Ce의 비교지수가 전부 "3.72 3.88
   3.88"로 동일 - 비교지수는 클래스별로 다른 게 아니라 펀드 전체가
   공유하는 시장지수라 당연한 것). `(row_kind, class_code, 1y값)`
   으로만 중복을 판정하던 기존 방식은 이 4개의 서로 다른 진짜 행을
   "같은 행이 중복 추출된 것"으로 오인해 1개만 남기고 나머지를
   지워버렸다. 페이지 안에서의 실제 세로 위치(_top)까지 같이 봐야
   서로 다른 행을 구분할 수 있어 이걸 키에 추가했다.
3. **(2번을 고치면서 새로 발견) 같은 표가 문서 안에서 통째로 두 번
   반복되는 문서도 있다** - 요약정보 섹션 + 뒤쪽 제2부 상세 섹션에
   같은 클래스의 값이 완전히 똑같이 두 번 인쇄돼 있어서(KR5153520012
   실측 - "C, C-P2e 없음"이라고 사용자가 별도로 지적해서 발견,
   2번을 고치자마자 반대로 진짜 중복이 살아나는 부작용으로 나타남),
   2번 수정만으로는 이 케이스가 전부 별도 행으로 남았다. class_fees.
   json이 "같은 클래스는 문서당 행 하나"로 통일하는 것과 같은 원칙으로
   맞췄다: class_code가 있는 행은 (product_code, class_code)로 하나만
   남기고, 확실성이 같으면 뒤쪽 페이지(제2부 상세표) 것을 남긴다(상세표
   쪽이 클래스 개수도 더 많이 나오는 걸 실측으로 확인해서 - 요약표엔
   없던 클래스가 상세표에만 있는 경우도 있었음 - 더 완전한 쪽으로
   판단, 사용자에게 확인받음). class_code가 없는 비교지수/변동성/
   투자신탁 합계 행은 "같은 (row_kind, 값 전부)"가 서로 다른 페이지에
   걸쳐 있을 때만(같은 페이지 안에서 값이 겹치는 건 2번 케이스처럼
   절대 안 건드림) 가장 뒤쪽 페이지 것만 남기도록 별도로 정리했다.

전체 재실행 후 재확인: 519건→637건(2번 수정 직후, 진짜 누락 복원)→
**588건**(3번 수정 후, 문서 반복으로 인한 진짜 중복 제거)/97개 문서.
전수 스캔 결과 (product_code, class_code) 중복 0건, "2y==3y" 같은
라벨 밀림 의심 행 0건. KR5120420091은 5개 클래스(초단기우량채/A/Ae/
C/Ce) 전부 자기 몫의 비교지수·변동성을 갖춘 15행으로, KR5153520012는

### AUM(운용규모)

처음엔 "데이터 자체가 없다"고 결론 냈었다. products 100개 문서 전체(텍스트+표)를
"순자산총액"/"설정액"/"설정원본"/"운용규모" 키워드로 뒤졌는데, 나오는 건 전부
(1) 기준가격 산정 방식을 설명하는 법적 정의 문구, 아니면 (2) "설정액 50억원
미만이면 소규모펀드"라는 경고 문구(286건 검색됐는데 전부 이 하나의
반복)뿐이었다. 간이투자설명서는 정기 갱신되는 정적 문서라 매일 바뀌는 AUM은
안 싣고 "금융투자협회 홈페이지(dis.kofia.or.kr)에서 확인하라"고만 안내한다고
생각했다.

**→ 이 결론은 틀렸었다.** 사용자가 "재무상태표 이런건 안 해도돼?"라고 물어서
다시 봤더니, **제3부.1.재무정보 "나.재무상태표"(또는 "가.요약재무정보")에
이 펀드 자체의 자산총계/부채총계가 실제로 있었다** - 정확한 단어("순자산총액"
등)로만 찾아서 이 계산된 숫자를 놓쳤던 것뿐이었다. `순자산총계 = 자산총계 -
부채총계`로 계산하면 그게 이 상품의 실제 AUM이다 (예: KR510902511M -
자산총계 5,711 - 부채총계 14 = 5,697백만원 = 56.97억원).

(참고: "운용전문인력" 표에 있는 "운용규모(억원)"는 여전히 이 상품 것이
아니라 **펀드매니저 한 명이 운용하는 전체 펀드 합산 규모**다 - 헷갈리기
쉬운 완전히 다른 숫자니 혼동하면 안 된다.)

**`extract_fund_aum.py` 구현** - "자산총계"라는 단어가 이 펀드 재무상태표
말고도 완전히 다른 곳(제4부. 집합투자기구 관련회사의 **운용사 자체 법인
재무제표**)에도 나와서 혼동하기 쉽다 - 거기는 "유동자산/고정자산" 같은
일반 기업회계 용어를 쓰는데(펀드 재무상태표는 "운용자산" 용어를 씀), 이걸
구분 못 해서 처음엔 KR5152420028 같은 문서에서 엉뚱하게 운용사 법인
재무제표(85,738백만원)를 이 상품 AUM으로 잘못 집을 뻔했다 - "유동자산"/
"고정자산"이 근처에 있으면 회사 재무제표로 보고 제외하도록 필터링했다.

여러 회계기간(기수)이 나란히 열거되는데 4개 문서로 표본 확인한 결과
일관되게 "가장 최근 기수가 첫 번째"였다. 단위(원/백만원)는 문서마다 달라
"단위: 백만원" 문구를 같이 찾아 `unit` 필드로 남긴다.

1차 결과는 85/100개 문서였다. 나머지 15개는 캐시된 텍스트(`extract_text()`)
에서 "재무상태표" 섹션 라벨("운 용 자 산", "자 산 총 계")이 글자 사이가
벌어진 폰트로 나와("운용자산"이라는 이어붙은 문자열 자체가 없음) 문자열
매칭이 실패한 것이었다. 총보수/수익률 표에서 겪은 "글자 간격이 좁아서
단어가 안 붙는" 문제와는 반대로, 이번엔 **의도적으로 넓은 자간의 라벨
폰트**라 `x_tolerance`를 올려도 해결되지 않는다 - 대신 좌표 기반으로 줄을
재구성한 뒤, 줄 텍스트에서 공백을 전부 지워 "자산총계"/"부채총계"를 찾고
숫자 토큰만 따로 뽑는 폴백(`extract_fund_aum_coordinates`)을 추가했다.

이 폴백 작업 중 두 가지를 더 발견해 고쳤다:
1. **일부 문서는 숫자까지 글자 단위로 쪼개져 나온다**("1 0 3 ,4 3 2 ,1 1 3
   ,0 0 5"). 같은 숫자의 조각은 토큰 간격이 ~0.2~0.5pt로 거의 붙어 있고,
   서로 다른 열(기수)의 숫자 사이 간격은 50pt 이상이라 이 간격 차이로
   조각을 합칠지 다음 열로 넘길지 구분했다. 처음엔 "직전 토큰 너비에
   비례한 임계값"을 썼는데, 이미 한 토큰으로 잘 뽑힌 긴 숫자("2,920,496,
   678,257" 같은 15자짜리)에서 그 비례값이 열 간격(70pt)보다 커져버려
   서로 다른 열의 숫자까지 하나로 합쳐버리는 회귀가 발생했다 - 고정
   임계값(3pt)으로 바꿔 해결.
2. **단위(원/백만원) 오판독**: 페이지 안에 재무상태표와 무관한 다른 표의
   "(단위: 백만원)" 표기가 먼저 나오는 경우(KR5127450473: 거래비용 표가
   먼저 나오고 그 아래 진짜 재무상태표는 "단위: 원"), 페이지 전체에서
   첫 번째 "단위" 언급을 집어버려 원래 "원" 단위인 값을 "백만원"으로
   잘못 곱해 실제보다 100만 배 부풀려진 값(18조원짜리 펀드로 오인)이
   나온 걸 발견 - "재무상태표"/"요약재무정보" 제목을 본 뒤에 나오는
   단위 표기만 채택하도록 수정.

기존 85건 재확인(회귀 없음) + 폴백으로 12건 추가 회복해 **97/100개
문서**. 원 단위 환산 시 최소 약 6.3억원~최대 약 4.78조원으로 상식적인
범위. `fund_aum` 테이블(다른 6축 테이블과 마찬가지로 `product_code` PK,
정답 데이터로 취급 - `manager_info`의 `is_product_aum=0`과 달리 여긴
실제 이 상품의 값)에 적재했다.

**"FUND에서 재무제표 있는 문서만 한거여? R2_KR514X450008 결과가 없는거
같은데"라는 지적으로 나머지 3개를 개별 확인함** — 셋 다 원본 텍스트에
직접 확인했다: KR5147430065는 "가. 요약 재무정보: 신규설정으로
해당사항 없음. 나. 재무상태표: 신규설정으로 해당사항 없음."
KR514X450008은 "제3부.1.재무정보 ... 설정 초이므로 해당사항 없음."
KR5153420339는 "1. 재무정보 가. 요약재무정보 해당사항없음 나.
재무상태표 해당사항없음." 셋 다 막 설정돼서 아직 결산을 한 번도 안 한

숫자가 없는 진짜 데이터 부재 케이스다. KR514X450008은 페이지 44에

펀드 재무상태표라면 안 나오는 말들)라서, `find_fund_balance_sheet`의
"운용자산" 키워드 필터가 (의도한 대로) 걸러내고 있었다.

**"evidence가 .22)로 끝나는데 이건 뭐야?"라는 지적으로 발견한 evidence
잘림 버그** — `evidence`를 "자산총계" 위치 기준 고정 글자수(앞 120자/뒤

".22)"라는 의미 없는 파편만 남는 문서(KR510902511M)가 있었다. 고정
글자수 대신 줄 단위로 재구성했다 - "자산총계" 줄 위쪽으로 헤더 줄(기수/
날짜 라벨이 있는 줄)을 찾아 거기서부터, "자산총계" 몇 줄 뒤(부채총계
포함)까지를 온전한 줄 단위로 이어붙인다. 헤더 표기가 문서마다 달라서
("항목"/"항 목"(글자 간격 벌어짐, KR5111420047)/"제 10 기"류/"14기
(24.12.22)"류) 이 중 하나라도 걸리면 헤더로 인식하도록 넓게 잡았다.
전체 재실행 후 재확인: 값(net_asset_latest 등) 변화 없음(97/100건
그대로, 범위도 동일), evidence만 줄 경계 기준으로 완전하게 재구성됨.

**"여기 숫자가 다른 게 있다"는 지적으로 발견한 진짜 값 오차 - 계산값 대신
원본이 직접 밝힌 "자본총계" 채택** — evidence를 다시 원본과 대조하다가
사용자가 숫자 불일치를 지적했다. 확인해보니 KR510902511M의 13기 순자산은
우리가 계산한 값(자산총계 9,235 - 부채총계 49 = 9,186)과 원본이 재무
상태표에 직접 적어놓은 "자본총계"(9,185)가 **1(단위: 백만원) 차이**가
났다. 원인은 회계상 흔한 반올림 오차 - "원본"/"수익조정금"/"이익잉여금"
같은 하위 항목이 각각 독립적으로 반올림돼 있어서, 자산총계·부채총계도
마찬가지로 반올림된 값이라 그 둘을 빼면 진짜 순자산(하위 항목을 직접
더한 값)과 ±1 차이가 날 수 있다. 우리가 자산총계-부채총계로 "계산"한 값은
정확히는 원본에 없는 파생값이었던 것이고, "자본총계"는 원본이 실제로
"이게 순자산입니다"라고 밝힌 값이라 이게 더 정확하다.

`자본총계`를 새로 정규식으로 찾아서, 있으면(개수가 자산총계/부채총계와
맞을 때만 - 다른 표의 걸 잘못 집을 위험 방지) 계산값 대신 이 값을
`net_asset_total`로 채택하도록 고쳤다. evidence에도 "부채총계"부터
"자본총계"까지 이어지는 전체 흐름을 보여주도록 범위를 넓혀서, 왜 이
값을 썼는지 바로 대조할 수 있게 했다. 전체 재실행 후 재확인: 97/100건
그대로, 계산값과 채택값 차이가 5(단위 기준) 이상 나는 이상 사례 0건(전수
스캔 - 큰 차이가 나면 다른 표를 잘못 집었다는 신호인데 그런 경우 없음
확인), **24개 문서**에서 ±1 수준의 반올림 오차가 실제로 보정됨.

**"법인세랑 자본금 어디서 찾은거야?"라는 지적으로 발견한 진짜 값 버그 -
운용사 자체 재무제표를 펀드 AUM으로 잘못 집음** — KR5144420091의
evidence를 보니 "법인세 7,225 / 자본금 40,000" 같은 일반 기업회계
항목이 있었다. 원본을 직접 대조해보니 이건 이 펀드가 아니라 제4부(집합
투자기구 관련회사) 섹션의 **운용사(NH-Amundi자산운용) 자체 법인
재무제표**("현금및예치금/유가증권/유형자산/예수부채/법인세/자본금/
이익잉여금/영업수익/영업이익" - 증권사·운용사의 일반 기업회계 계정과목,
펀드의 포트폴리오 구성과는 무관)였다. `find_fund_balance_sheet`의
"운용자산" 필터가 "이 단어가 페이지 어딘가에 있으면 통과"였는데,
공교롭게도 이 회사 재무제표 바로 아래에 "라. 운용자산규모"라는 완전히
다른 섹션(운용사가 운용하는 전체 펀드의 유형별 규모 통계) 제목이 같은
페이지에 있어서 그 우연한 일치로 필터를 통과해버린 것이었다.

고치면서 재확인해보니 같은 운용사(NH-Amundi) 산하의 다른 펀드
KR5144420081도 같은 회사 재무제표(완전히 동일한 숫자 - 162,972/
150,195)를 잘못 집고 있었다(이번엔 좌표 기반 폴백 경로에서 - 처음
정규식 경로만 고쳤을 때 이 문서가 폴백으로 넘어가면서 발견). "운용자산"
이 자산총계 근처에 있는지로(페이지 전체가 아니라) 범위를 좁혔는데,
처음엔 "자산총계 앞쪽 400자만" 봤다가 KR5114420027처럼 "자산총계"가
소계로 먼저 나오고 "운용자산"이 그 *다음* 줄에 오는 반대 순서 문서
6개(KR5114420016/022/027/046/KR5114450222/270)를 회귀로 놓칠 뻔했다
(양쪽 다 실측으로 확인된 정상 패턴이라 어느 한쪽만 보면 안 됨) - 앞뒤
양쪽을 다 보되 "운용자산규모"는 부정형 전방탐색(`(?!규모)`)으로 제외하는
정규식(`OPERATING_ASSET_RE`)으로 최종 정리했다. 두 추출 경로
(`find_fund_balance_sheet`/`extract_fund_aum_coordinates`) 모두 같은
정규식으로 통일해 적용.

전체 재실행 후 재확인: KR5144420091은 140,130백만원(회사 자본총계, 틀린
값) → 721,830,399,875원(펀드 자산총계-부채총계, page 44 실측과 일치)로
정정. 6개 letter-spacing 문서는 원래 값 그대로 유지(회귀 없음).
KR5144420081은 원본이 펀드 자체 재무상태표를 심하게 뒤섞인 2단
레이아웃("제 6 기 제 5 기... 운 증 파..." 글자 단위로 두 칸이 교차
배치됨)으로 내보내서 좌표 재구성으로도 아직 못 읽어 - 잘못된 회사
숫자를 보여주는 것보다 낫다고 보고 96/100건으로 하나 줄여서(97→96) 없는
값으로 남겼다(추후 이 문서 전용 다단 표 재구성이 필요하면 별도 작업).
나머지 95건은 값 변화 없음.

**"회사 관련은 다 뺀거지? 내가 확인할때 어떤거 봐야 알 수 있어?"라는
질문에 답하려고 전수 재검사함** — 96건 전체 evidence를 두 가지로
스캔했다: (1) 법인세/자본금/주요주주/예수부채/유형자산/무형자산/
영업수익/영업이익/당기순이익/이연법인세 같은 **회사 재무제표 전용
용어**가 섞여 있는지(0건), (2) 반대로 **펀드 재무상태표의 특징적 항목인
"운용자산"**이 evidence에 실제로 보이는지(글자 간격이 벌어진 문서는
공백을 지우고 비교 - 처음 스캔 땐 "운 용 자 산"처럼 떨어진 표기를
못 찾은 문서가 있어서 8건이 빠진 것처럼 보였는데, 공백 무시하고 다시
보니 실제로는 다 있었다). 그 과정에서 좌표 기반 폴백 경로
(`extract_fund_aum_coordinates`)의 evidence가 원래 "자산총계 .../
부채총계 ..."만 보여줘서, 내부적으론 "운용자산"이 근처에 있는지 확인해
놓고도 그 확인 근거 자체는 evidence에 안 보여주고 있었다는 걸 발견해 -
"운용자산"이 걸린 줄의 원문을 evidence 맨 앞에 같이 남기도록 고쳤다.

**그래서 검증할 땐 이 두 가지만 보면 된다**: evidence에 (1) "운용자산"
(또는 letter-spacing이면 "운 용 자 산"처럼 벌어진 표기) 항목이 실제로
있는지, (2) 법인세/자본금/주요주주/예수부채/유형자산/무형자산/영업이익
같은 일반 기업회계 용어가 섞여 있진 않은지. 재검사 결과 96건 전부
(2)는 0건, (1)은 전부 확인됨(공백 유무와 무관하게 전수 재스캔 - 코드로
직접 돌려 확인, 표본이 아님).

**"confidence가 0.8인거 있는데 그러면 안 되는거 아녀?"라는 지적으로
고정 confidence를 실제 확실성 반영값으로 바꿈** — `extract_fund_aum.py`의
두 추출 경로(`extract_fund_aum`/`extract_fund_aum_coordinates`)가 실제로
얼마나 확실한지와 무관하게 둘 다 `confidence: 0.8`을 그냥 고정값으로
박아뒀었다. `class_fees`/`class_returns`는 이미 "class_code를 못 찾으면
0.5로 낮춘다"처럼 confidence가 실제 근거의 확실성을 반영하는데, `fund_aum`
만 이 관례를 안 따르고 있었던 것 - 사용자 지적이 맞았다. 캐시된 텍스트에서
"자산총계 N N N"을 정규식으로 바로 잡아내는 `text_regex` 경로는 재구성
단계가 없어 오차 여지가 적고, `coordinate_reconstruction`(글자 간격이
벌어진 라벨을 좌표로 다시 붙이고 숫자도 토큰 간격 임계값으로 조각을
합칠지 판단하는 폴백 경로)은 그 재구성 자체가 추가 오차 요인이라 - 처음엔
전자 0.9, 후자 0.75로 나눴다.

**"아니 근데 1이여야하는거 아니니"라는 재지적으로 한 번 더 정정** —
`class_fees`가 매기는 기준을 다시 보면 "class_code를 깔끔하게 찾음
= 1.0" / "못 찾음(불확실) = 0.5"다. `text_regex` 경로는 "운용자산"이
자산총계 근처에 있는지 확인(회사 재무제표 배제)까지 마친 뒤 "자산총계
N N N"을 정규식으로 바로 잡아낸, 재구성 단계 없는 깔끔한 구조적
매치라 - class_fees의 "class_code 깔끔하게 찾음" 케이스와 성격이 완전히
같다. 0.9로 애매하게 깎아둔 게 오히려 이 프로젝트 관례와 안 맞았던
것 - `text_regex`는 1.0으로 올리고, `coordinate_reconstruction`(정규식
으로 못 찾아서 좌표+숫자조각 병합 휴리스틱으로 우회한 경로 - class_fees의
"확신 못해서 낮춘" 케이스와 같은 성격)은 0.75 그대로 뒀다.

전체 재실행 후 재확인: 값(asset_total 등)은 전부 그대로(96/100건 유지),
confidence는 `text_regex` 83건 → **1.0**, `coordinate_reconstruction`
13건 → **0.75**로 최종 정리됨.

**"class_code를 깔끔하게 찾았다 = 1.0"이 기준이어도 되는 거냐, 다 제대로
뽑아야 1이어야 하는 거 아니냐는 근본적인 지적** — 맞는 말이었다. 지금
confidence는 "이 행의 모든 필드가 다 맞다"가 아니라 **"이 행을 어떤
클래스/어떤 상품 것인지 헷갈릴 위험이 없는가"**(class_fees는
class_code, fund_aum은 자산총계·부채총계가 회사 재무제표가 아닌지)만
본다. 실제로 이번 세션에서 고친 버그 대부분(sales_commission_desc가
null이었던 것, 인접 클래스명끼리 섞였던 것, 운용전환일 전/후 값을
놓쳤던 것 등)이 전부 **class_code는 처음부터 confidence 1.0으로 정확히
찾혀 있던 행**에서 나왔다는 게 이 한계를 실측으로 보여준다.

total_fee/판매수수료 문구/클래스명 표기/unit 판별처럼 서로 다른 이유로
서로 다른 곳에서 틀릴 수 있는 필드들을, "확실성"이라는 하나의 숫자로
합칠 원칙적인 근거가 없어서(가중치를 어떻게 매겨도 자의적임) 필드명이나
값 체계를 새로 만드는 대신, **confidence가 정확히 뭘 보장하는지를
`build_product_facts_db.py`/`extract_class_fees.py`/`extract_fund_aum.py`
docstring·주석에 명시**하기로 했다. "행 전체가 실제로 맞는지"를 실질적으로
담보하는 건 confidence 숫자가 아니라, 이 프로젝트 전체에서 매 수정마다
돌려온 **전수 이상치 검사**(class_fees: 1y>500/1y<10/total_fee>10/
distribution_fee>total_fee/total_fee_and_cost<total_fee/class_code
중복 0건; fund_aum: 자산총계≥부채총계, 원 단위 환산 시 상식적 범위
등)라는 점도 같이 적어뒀다.

**추가: 운용역 합산 규모를 참고용으로만 저장 (`extract_manager_info.py`)**
사용자가 위 "운용전문인력" 표를 다시 가리키며 재확인을 요청해서, 같은
매니저가 여러 상품 문서에 등장하는 경우(KR510902511M/KR5110601022 둘 다
"송진용, 37개 펀드, 15,747억원"으로 동일 반복) 또는 한 문서 안에 매니저가
2명 있어 서로 다른 합산 규모가 나란히 나오는 경우(KR5125450023: 김화진
24개/19,788억원, 박영훈 17개/18,663억원)를 다시 보여줘서, 이 값이 상품
단위가 아니라는 걸 다시 한 번 근거로 확인했다. 6축 정답으로는 안 쓰되,
아예 버리지 말고 참고 정보로 저장하기로 했다 (`is_product_aum=false`로
명시).

이름+생년+운용기구수(개)+운용규모(억원) 패턴을 좌표 기반 줄 재구성으로
찾는 정규식 매처로 구현했다(`MANAGER_RE`) - 직위 라벨("본부장", "책임\n
(팀장)" 등)이 문서마다 길이가 달라 생년과 기구수 사이를 non-greedy로
건너뛰게 했다. 47개 행(39개 문서)을 뽑았고, `manager_info` 테이블에
`is_product_aum=0`을 고정값으로 박아 넣어 다른 6축 테이블과 절대 안
섞이게 분리했다. 나머지 61개 문서는 이 정규식 패턴에 안 걸린 것으로,
정식 축이 아니므로 더 파고들지 않았다.

### 상품 비교 질의 - 구조화 DB 직접 조회로 토큰 절약

`product_master.json`/`class_fees.json`/`class_returns.json`을 만들어놓고도
검색 파이프라인에 안 붙어 있으면 무용지물이다 - "A상품이랑 B상품 총보수
비교해줘" 같은 질의가 오면 지금까지는 semantic_search로 각 상품 문서에서
텍스트 청크를 여러 개 긁어와 LLM에 던지는 방식뿐이었는데, 이미 정확한
숫자를 구조화해뒀으니 그걸 직접 조회하는 게 훨씬 짧고 정확하다.

`build_product_facts_db.py`로 위 3개 JSON을 `structured_store.db`에
`product_master`/`class_fees`/`class_returns` 표로 적재하고(기존 표 전문
검색용 `tables`/`tables_fts`와 같은 DB 파일 공유), `compare_products.py`가
질의에서 상품코드(KR로 시작하는 패턴) 2개 이상을 인식하면(또는 "비교"/
"차이" 등 키워드 + 코드 1개) 이 표에서 필요한 필드만 SQL로 직접 조회해서
짧은 문자열로 반환한다.

구현하면서 발견한 문제: 총보수 표는 클래스가 여러 개(A/C/A-E/C-E 등) 다
있는데, 수익률 표는 보통 대표 클래스 하나만 싣는다(예: KR5127420034는
`class_fees`에 4개 클래스가 있지만 `class_returns`엔 C클래스만 있음). 총보수
기준으로 클래스를 먼저 고르면 수익률이 없는 클래스를 골라버릴 수 있어서,
**수익률이 있는 클래스를 먼저 정하고 총보수를 그 클래스에 맞춰 조회**하도록
순서를 바꿨다 - 안 그러면 "총보수(A-E클래스) vs 수익률(C클래스)"처럼 같은
상품 안에서 서로 다른 클래스 숫자가 섞여 나와 비교가 무의미해진다.

`api/server.py`의 `/answer`에도 연결해서, 질의에 상품코드가 2개 이상이면
`route_search`(semantic_search) 대신 이 경로를 먼저 타도록 했다. 대략적인
글자 수 비교로 봐도 압축 버전(2개 상품 요약, 약 210자)이 기존 방식(청크
6개 기준 약 2,300자)보다 10배 이상 짧다 - 실제 토큰 수는 한국어 특성상
글자 수와 정확히 비례하지 않지만 절감 폭의 크기는 비슷하다.

## 사용법

### 단일 파일 처리 (기존 방식)

```bash
pip install -r requirements.txt --break-system-packages

# 표 + 텍스트 추출 (PDF 전용, DOCX/XLSX/PPTX는 extractors.py의 extract_any() 사용)
python scripts/extract_tables.py \
    --input data/institution/doc1.pdf \
    --output extracted/institution/doc1_tables.json \
    --output-text extracted/institution/doc1_text.json

# 텍스트를 청크로 분할
python scripts/chunk_text.py \
    --input extracted/institution/doc1_text.json \
    --output extracted/institution/doc1_chunks.json \
    --source-doc doc1.pdf
```

특정 페이지 범위만 처리하려면 `--start`, `--end` 옵션 사용.

### 전체 파이프라인 (일괄 추출 → 구조화 저장소 → 벡터 저장소)

```bash
pip install -r requirements.txt --break-system-packages

# 1. data/institution, data/products 전체를 병렬로 추출 + 청크 생성
#    (PDF/DOCX/XLSX/PPTX 모두 처리, extracted/ 아래에 저장, 이미 처리된 문서는 스킵)
python scripts/extract_all.py --workers 4

# 2. 표 데이터를 SQLite(FTS5)로 구조화 (세액공제 한도, 위험등급, 총보수 등 키워드 검색용)
python scripts/build_structured_store.py

# 3. 청크를 임베딩해서 Chroma 벡터 저장소에 적재
python scripts/build_vector_store.py --reset

# 4. 검색 인프라 수동 점검
python scripts/search.py --query "DC와 DB, 운용 주체가 어떻게 다른가요?" --mode semantic
python scripts/search.py --query "세액공제" --mode table
```

`scripts/search.py`의 `semantic_search()` / `table_search()`는 다음 단계(질의 라우팅,
HyperCLOVA X 파이프라인, 평가용 API 서버)에서 그대로 import해서 쓰도록 설계했다.
두 함수 모두 결과에 `doc_id` / `source_doc` / `page` 등 근거 메타데이터를 포함한다.

### 임베딩 프로바이더

`scripts/embeddings.py`가 임베딩 구현을 추상화한다 (`EMBEDDING_PROVIDER` 환경변수 또는
`--provider` 옵션으로 선택).

| 이름 | 설명 | 상태 |
|---|---|---|
| `tfidf` (기본값) | 문자 n-gram TF-IDF + TruncatedSVD(LSA), 코퍼스에 자체 fit, API 키/모델 다운로드 불필요 | 동작 확인 |
| `sentence_transformers` | 다국어 sentence-transformers 모델 로컬 추론 (`intfloat/multilingual-e5-small`) | 이 개발 환경은 `huggingface.co` 아웃바운드가 정책상 막혀 있어 모델을 받지 못해 **미검증**. 접근 가능한 환경에서 전환 권장 |
| `hyperclova` | 네이버 클로바스튜디오 임베딩 API | API 키 미발급으로 **미검증**. 키 발급 후 엔드포인트/응답 스키마 확인 필요 |

`tfidf`는 코퍼스 자체에 fit해야 하므로 상태(벡터라이저 + SVD)를
`vector_store/chroma/embedding_provider.pkl`에 저장하고, 검색 시 그대로
불러와 같은 벡터 공간에 질의를 투영한다. `build_vector_store.py`를 다시
돌리면(특히 `--reset`) 이 상태도 다시 fit되므로, 문서가 추가되면 재적재가 필요하다.

### 질의 라우팅

`scripts/router.py`가 자연어 질의를 institution(제도/세제) / products(상품) /
복합으로 분류하고, `search.py`의 `semantic_search` / `table_search`를 알맞게
호출해서 근거 후보를 모은다. HyperCLOVA X 키가 아직 없어서 지금은 키워드
규칙 기반 분류(`classify()`)이고, 키가 생기면 이 함수만 HCX 의도분류로
교체하면 된다(`route_search()`의 반환 스키마는 그대로 유지).

```bash
python scripts/router.py --query "연금저축이랑 IRP에 넣으면 세액공제 얼마까지 되나요?"
```

## 평가용 API 서버

대회 스펙(요청/응답 규격)에 맞춘 API 서버가 `api/server.py`에 있다.

```
GET {endpoint}/answer?question_id={id}&question={질의}
-> 200 application/json
{
  "question_id": "...", "question": "...",
  "retrieved_context": "...", "think_trace": "...", "answer": "..."
}
```

로컬 실행/테스트:

```bash
uvicorn api.server:app --host 0.0.0.0 --port 8000

curl -G "http://127.0.0.1:8000/answer" \
    --data-urlencode "question_id=Q-001" \
    --data-urlencode "question=DC와 DB, 운용 주체가 어떻게 다른가요?"
```

**현재 상태**: 라우팅 + 검색(`retrieved_context`, `think_trace`)까지는 실제로
동작한다. `answer` 필드는 아직 HyperCLOVA X API 키가 없어서 진짜 LLM 생성이
아니라 검색된 근거를 발췌해서 보여주는 임시 스텁이다(`api/server.py`의
`generate_answer()`에 `TODO` 표시). 키가 발급되면 이 함수만 HCX Chat
Completions 호출로 교체하면 나머지(라우팅, 검색, 응답 스키마)는 그대로 쓸 수
있다.

**제출용 API End-point**: `[TODO — 네이버클라우드 또는 개인 서버에 배포 후
실제 접속 가능한 URL로 채울 것. 대회 규정상 README에 명시 필수]`
표준 포트(HTTP 80 / HTTPS 443, self-signed 인증서 허용) 사용, 별도 인증
헤더 없음, `/answer` 경로 고정, GET만 지원.
